# pjm-pfd-replan

When a project planned with `pjm-pfd-estimation-plan` is delayed, reflect the progress table `<project>/progress.tsv` and redraw the plan. Do not change the master `ap.tsv` or the estimate boxes on the PFD (to preserve the original estimates and allow a retrospective on estimation accuracy). Ticket-system-specific processing (fetching progress, writing dates back) is not part of this skill.

This skill builds on the procedures and conventions of `pjm-pfd-estimation-plan`. Read `pjm-pfd-estimation-plan/SKILL.md` in the same plugin first.

## Workflow

- [ ] 1. Confirm the working language: ask the user whether to proceed in 日本語 or English. Use the chosen language for all subsequent conversation, explanations, progress reports, and lint / critical-path summaries. (Command names, paths, option flags, column names, and code stay verbatim regardless of the chosen language.)
- [ ] 2. Confirm the prerequisites ([Prerequisites](#prerequisites))
- [ ] 3. Prepare progress.tsv (create it if missing) and validate it ([Progress Table](#progress-table))
- [ ] 4. Triage the end-date risk and report it ([Triage](#triage))
- [ ] 5. Back up the previous outputs ([Backup](#backup))
- [ ] 6. Confirm the replan start date ([Replan Start](#replan-start))
- [ ] 7. Re-derive the scenario tables with the remaining work volumes ([Derive Residual Scenario Tables](#derive-residual-scenario-tables))
- [ ] 8. Regenerate lint → plan-json → outputs ([Regenerate Plan And Outputs](#regenerate-plan-and-outputs))
- [ ] 9. Present the diff between the old and new timelines ([Timeline Diff](#timeline-diff))
- [ ] 10. (Optional) Review the estimates of completed processes ([Retrospective](#retrospective))

## Conventions

- At the start, confirm the working language (日本語 / English) with the user, then use it consistently for all conversation, explanations, and progress reports. Keep command names, paths, options, and column names verbatim.
- Follow the Conventions of estimation-plan for the search-quality fallback (if `-poor` does not finish within 20 seconds, use `-poorest`; once you switch one, switch all of them from then on).
- Replanning is a global re-optimization, so the start and end of processes that are not delayed can also change. If reproducibility is required, use `-poorest` (deterministic). Keep ticket updates to the minimum needed, based on the diff in [Timeline Diff](#timeline-diff).
- The criticalpath / pfdquery in [Triage](#triage), the fallback generation during backup, the timeline TSV for the diff, and [Timeline Diff](#timeline-diff) are all done with the **scenario used as the basis for ticket dates** (default: optimistic. Setting deadlines on the pessimistic scenario makes work expand to fill the time by Parkinson's law, so deadlines use the optimistic scenario and the pessimistic scenario is used as the range of uncertainty). The command examples in this document are written for the optimistic scenario; if the basis scenario is pessimistic, read `optimistic` in file and setting names as `pessimistic`.
- Depending on the user's requests, you may need to investigate changes, successor processes, and so on; pfd-tools can help with this. In that case, run `pfdhelp -short` to see the descriptions of the pfd-tools tools.

## Prerequisites

Confirm the following. If anything is missing, run `pjm-pfd-estimation-plan` first:

- A bootstrapped project (master `ap.tsv`, scenario settings files `project_optimistic.json` / `project_pessimistic.json`, `holidays_ja.txt`)
- The previous plan outputs: `plan_optimistic.json` / `plan_pessimistic.json`, and the timelines (`timeline_*.tsv` or `plan_*.mmd`)
- The previous critical-path analysis results `criticalpath_*.tsv` (if the one for the basis scenario is missing, generate it at the start of [Triage](#triage))

## Progress Table

`<project>/progress.tsv` is a ticket-system-independent intermediate format for progress, holding the remaining work volume per atomic process (`残楽観作業量` = remaining optimistic work volume, `残悲観作業量` = remaining pessimistic work volume):

```tsv
ID	残楽観作業量	残悲観作業量
P1	0	0
P2	0.5	1
P3
```

| Value | Meaning |
|---|---|
| Both columns blank, or no row | Not started (original estimate stays) |
| `0` | Completed |
| Positive number | Remaining work volume (business days; same unit as the estimate boxes) |

**A missing `<project>/progress.tsv` is not a failed prerequisite. If it is missing, create it here** (do not abort this skill). Create a new file with only the header row `ID`, `残楽観作業量`, `残悲観作業量` (tab-separated), and, based on the ID set from `pfdesttable <project>/pfd.drawio.png`, fill in **rows only for completed and in-progress processes**. Processes without a row are treated as not started, so you do not need to list every ID. Ask the user for the remaining work volumes.

Validate before applying:

- Each `ID` exists as an atomic process in the PFD (check against the ID set from `pfdesttable <project>/pfd.drawio.png`; warn about nonexistent IDs and confirm their exclusion)
- `残楽観作業量` ≤ `残悲観作業量` (when both are filled in)
- Filling in only one of the two is an error (fill in both or leave both blank)
- Negative values are an error

## Triage

Before replanning, determine and report first **whether the planned end date of the basis scenario for deadlines (the foundation of ticket deadlines) moves**. If a worker only wants to decide whether escalation is needed based on the expected delay of their own process, use `pjm-pfd-delay-triage`, which can run this triage on its own. Use the previous `criticalpath_optimistic.tsv` (the one for the scenario used as the basis for deadlines; see [Conventions](#conventions)). If it is missing, generate it now, while the scenario tables are still the previous ones (this gives an analysis of the previous plan; if `-poor` does not finish within 20 seconds, use `-poorest`):

```console
$ criticalpath -f <project>/project_optimistic.json -poor > <project>/criticalpath_optimistic.tsv
```

Count the delay in business days as the number of business days from "the process's scheduled end date in the old plan" to "the end date expected now (re-estimated from the remaining work volume)":

- The delayed process's delay in business days ≤ that process's `最大弾性値（全余裕）` (maximum elasticity, i.e. total float) → the basis scenario's planned end date does not move (no full redraw of ticket deadlines is needed).
- Delay > total float, or multiple processes are delayed at the same time, or the estimates themselves were revised → replan on the assumption that the planned end date moves.
- For the risk to external commitments (dates promised on a pessimistic basis), make the same judgment using the total float in `criticalpath_pessimistic.tsv` and report it as well (if exceeded, say that a date adjustment with stakeholders is likely to be needed).

Also present the scope of impact (successor processes whose dates may move):

```console
$ pfdquery -f <project>/project_optimistic.json -reachable <delayed process ID>
```

The `REACHABLE` rows list the delayed process itself and the successor processes reachable from it. **Pass only process IDs to `-reachable`** (there is a known issue where passing a deliverable ID causes a panic).

Triage caveats:

- Triage judges end-date risk; it does not mean skipping date updates. **Even if the delay is within total float, the start and end dates of serial successors move**, so always recompute the dates in the subsequent replanning. Do not manually shift all successors uniformly, since that ignores resource conflicts.
- Elasticity values are relative to the previous plan and previous estimates, and are shared among processes on the same path. Do not judge multiple delays by adding and subtracting elasticity values (when in doubt, replan).
- Total float is relative to the greedy-search plan and can be negative; treat negative values as 0 (no total float).

## Backup

Before re-deriving and regenerating, copy whichever previous outputs exist into `<project>/replan/<YYYYMMDD>/` as a backup (it becomes the comparison baseline for [Timeline Diff](#timeline-diff)):

```console
$ mkdir -p <project>/replan/<YYYYMMDD>
$ cp <project>/ap_optimistic.tsv <project>/ap_pessimistic.tsv <project>/plan_optimistic.json <project>/plan_pessimistic.json <project>/timeline_*.tsv <project>/plan_*.mmd <project>/criticalpath_*.tsv <project>/replan/<YYYYMMDD>/ 2>/dev/null || true
```

If there is no old timeline TSV (mermaid workflow), generate one **at this point** from the previous plan-json and put it in the backup directory. It can only be reproduced correctly now, while the scenario tables and the scenario settings' `start_day` still hold the previous contents (override only the output format, and let the start date and business hours be read from the settings file):

```console
$ plantimeline -f <project>/project_optimistic.json -out-format google-spreadsheet-tsv <project>/plan_optimistic.json > <project>/replan/<YYYYMMDD>/timeline_optimistic.tsv
```

## Replan Start

Confirm the replan start date (the day planning of the remaining work begins; default: the next business day) with the user, and update `start_day` in **all scenario settings files** to the same date (the old value can be traced in git history). Subsequent timeline rendering uses this `start_day`, so there is no need to pass `-start` on the command line again.

## Derive Residual Scenario Tables

Re-derive `ap_optimistic.tsv` / `ap_pessimistic.tsv` using the queries from estimation-plan's Derive Scenario Tables with the following two modifications (apply the other branches, such as the rework-edge format and the coarse-granularity resource default, unchanged):

1. Append `LEFT JOIN <project>/progress.tsv AS t3 ON t1.ID = t3.ID` to the end of the `FROM` clause
2. Replace the `予想作業量` expression with `CASE WHEN LENGTH(t3."残楽観作業量") > 0 THEN t3."残楽観作業量" ELSE t1."楽観作業量" END` (for pessimistic, `残悲観作業量` / `悲観作業量`)

For processes with no row in progress.tsv or with blank cells, the LEFT JOIN result is NULL or an empty string, so `LENGTH(...) > 0` is false and the original estimate is used.

Example without rework edges at fine granularity (optimistic. For pessimistic, read `楽観`→`悲観` and `0.1`→`0.3`. `$(pfdres <count>)` is handled the same as in estimation-plan):

```console
$ pfdesttable <project>/pfd.drawio.png | qhs -H -O -t -T "SELECT t1.ID, t2.\"説明\", CASE WHEN LENGTH(t3.\"残楽観作業量\") > 0 THEN t3.\"残楽観作業量\" ELSE t1.\"楽観作業量\" END AS \"予想作業量\", 0.1 AS \"予想手戻り作業量割合\", CASE WHEN LENGTH(t2.\"楽観必要資源\") > 0 THEN t2.\"楽観必要資源\" ELSE '$(pfdres <optimistic worker_count>)' END AS \"必要資源\", '' AS \"開始条件\" FROM \"-\" AS t1 JOIN <project>/ap.tsv AS t2 ON t1.ID = t2.ID LEFT JOIN <project>/progress.tsv AS t3 ON t1.ID = t3.ID" > <project>/ap_optimistic.tsv
```

After deriving, Read a few lines to confirm the remaining work volumes were applied, and report to the user the counts of completed (0), started (remaining volume), and not-started (original value) processes.

## Regenerate Plan And Outputs

Rerun estimation-plan's Project Files And Lint → Generate Plan JSON → output generation (GitHub + Mermaid or Google Sheets Timeline, plus Master Schedule if needed) with the same procedure. The only differences:

- The start date for timeline rendering is read from the `start_day` updated in [Replan Start](#replan-start) (do not pass `-start` again)
- Even when the output format is `mermaid`, also generate a timeline TSV for [Timeline Diff](#timeline-diff) (override only the output format):

  ```console
  $ plantimeline -f <project>/project_optimistic.json -out-format google-spreadsheet-tsv <project>/plan_optimistic.json > <project>/timeline_optimistic.tsv
  ```

- Also rerun `criticalpath` for both scenarios to update `criticalpath_optimistic.tsv` / `criticalpath_pessimistic.tsv` (the one for the basis scenario becomes the baseline for the next triage)

## Timeline Diff

Compare the old and new timeline TSVs and present the list of processes whose start or end changed. These are the candidates for reflecting dates into the ticket management system.

With feedback loops, the timeline TSV has multiple rows per (process, completion count), so first aggregate per process (start = first start, end = last end). Tickets are per process, so this granularity also fits the update (qhs does not support subqueries in the FROM clause, so split it into two steps):

```console
$ qhs -H -O -t -T "SELECT \"AtomicProcess\", \"Description\", MIN(\"StartTime\") AS \"StartTime\", MAX(\"EndTime\") AS \"EndTime\" FROM <project>/timeline_optimistic.tsv GROUP BY \"AtomicProcess\"" > <project>/timeline_optimistic_agg.tsv
$ qhs -H -O -t -T "SELECT \"AtomicProcess\", \"Description\", MIN(\"StartTime\") AS \"StartTime\", MAX(\"EndTime\") AS \"EndTime\" FROM <project>/replan/<YYYYMMDD>/timeline_optimistic.tsv GROUP BY \"AtomicProcess\"" > <project>/replan/<YYYYMMDD>/timeline_optimistic_agg.tsv
```

JOIN the aggregated old and new tables and extract only the processes whose dates changed. Exclude completed processes (remaining = 0) (so as not to overwrite actual dates on tickets). The output columns `旧開始` / `新開始` / `旧終了` / `新終了` are old start / new start / old end / new end:

```console
$ qhs -H -O -t -T "SELECT n.\"AtomicProcess\", n.\"Description\", o.\"StartTime\" AS \"旧開始\", n.\"StartTime\" AS \"新開始\", o.\"EndTime\" AS \"旧終了\", n.\"EndTime\" AS \"新終了\" FROM <project>/timeline_optimistic_agg.tsv AS n JOIN <project>/replan/<YYYYMMDD>/timeline_optimistic_agg.tsv AS o ON n.\"AtomicProcess\" = o.\"AtomicProcess\" LEFT JOIN <project>/progress.tsv AS p ON n.\"AtomicProcess\" = p.ID WHERE (n.\"StartTime\" <> o.\"StartTime\" OR n.\"EndTime\" <> o.\"EndTime\") AND (LENGTH(COALESCE(p.\"残楽観作業量\", '')) = 0 OR CAST(p.\"残楽観作業量\" AS REAL) <> 0)"
```

qhs reads blank cells as NULL. The completed-process exclusion absorbs NULL with `COALESCE` (the form `NOT (LENGTH(...) > 0 AND ...)` would make LENGTH(NULL) NULL and, under three-valued logic, drop not-started rows too).

Even for a delay within total float, serial successors (e.g., P3 following the delayed P1) appear in this diff and parallel processes that do not move do not, so ticket updates are kept to the minimum. If the diff is large (dates of non-delayed processes also moved widely), present it with a note that the global re-optimization rearranged the plan.

## Retrospective

(Optional) For completed processes (remaining = 0), present the list of original estimates (the `pfdesttable` output) and encourage comparing them with actuals and reflecting on them. Actual durations are information on the ticket management system side, so this skill does not handle them.

## Notes

- A `予想作業量` of 0 in ap.tsv is rounded up internally by pfd-tools to a minimum of 0.001. Completed processes finish as "nearly instantaneous tasks" right after the new start date, and successors' starts shift later by 0.001 business days each (about 30 seconds with `duration: 8`). This is negligible for day-granularity ticket updates.
- Completed processes line up with nearly zero length at the head of the new timeline. Exclude them when reading the Gantt / timeline (in Google Sheets, you may hide the completed rows).
- Do not set processes in the middle of a feedback loop to 0. Fill in a remaining work volume that accounts for the remaining iterations (treating them as completed makes the subsequent rework cost be regarded as nearly 0).
